
# Phase 4 Notes: The Rest of the DevOps Toolchain (Weeks 17–20)

You can already provision real, multi-tier AWS infrastructure with Terraform — that's the hard part. Phase 4 is shorter on new "concepts" and more about the surrounding habits and tools that make you look like someone who's actually worked on a team, not just followed tutorials alone. ## Week 17: Git and GitHub, Properly

You've been using `git add / commit / push` to get projects onto GitHub since Phase 3 — that's fine for solo work, but real teams use a few more habits that are worth building now, while it's low stakes.

### Branching

Working directly on `main` is fine for a personal experiment, but the habit worth building is:

```bash
git checkout -b feature/add-rds-multi-az
# make your changes
git add .
git commit -m "Add Multi-AZ support to RDS module"
git push -u origin feature/add-rds-multi-az
```

Then open a **Pull Request (PR)** on GitHub from that branch into `main`, instead of pushing straight to `main`.

**Why bother, if you're working alone?** Two reasons that matter for the job search specifically:

1. It's the workflow every team actually uses — practicing it now means it's second nature in an interview or your first week on a job, not something you're learning under pressure.
2. It sets up Week 19's CI/CD step — a PR is exactly where an automated `terraform plan` check becomes useful, giving you visible proof (in the PR itself) that your change is safe before it merges.

### Writing commit messages that don't waste anyone's time

`fixed stuff` tells a reviewer nothing. Aim for a short summary of *what* changed and, if it's not obvious, *why*:

```
Add NAT Gateway to private subnet route table

Private instances couldn't reach the internet for OS updates.
```

### `.gitignore` for Terraform projects

You've been doing a rough version of this since Phase 2 — here's the complete list and *why* each line matters:

```gitignore
# Local Terraform working files — regenerated by `terraform init`, never commit
.terraform/

# State files often contain sensitive data (passwords, keys as attributes)
*.tfstate
*.tfstate.backup

# Variable files often contain secrets (DB passwords, API keys)
*.tfvars
!*.tfvars.example

# Crash logs, if Terraform ever crashes
crash.log
```

**One important exception:** `.terraform.lock.hcl` should be **committed**, not ignored. This is the provider dependency lock file (similar in spirit to `package-lock.json` in Node projects) — it pins the exact provider versions/checksums your config was tested against, so a teammate (or your CI pipeline) gets the exact same provider versions you did. Leaving it out of git is a common beginner mistake that causes "works on my machine" problems.

Since real `.tfvars` files are gitignored, provide a `terraform.tfvars.example` alongside your code showing the expected variable names and format with placeholder values — this is what lets someone else clone your repo and actually run it.

### Checkpoint

Go back to all three Phase 3 projects: make sure each has a proper `.gitignore`, a committed `.terraform.lock.hcl`, and a `terraform.tfvars.example` if the original committed real values by mistake. Do this work on a feature branch and open a real PR to merge it — practice the workflow, not just the content.

## Week 18: Docker Fundamentals

Terraform provisions infrastructure; Docker packages *applications* so they run identically anywhere. Most real DevOps roles expect both, and Phase 3's `aws_instance` + `user_data` pattern doesn't scale well once an app gets more complex than "install httpd and echo a string."

### Container vs. VM — the distinction that matters

A **virtual machine** (like your EC2 instances) virtualizes an entire computer, including its own OS kernel. A **container** shares the host machine's kernel and only packages the application plus its dependencies — this makes containers dramatically lighter and faster to start than VMs.

```
VM:                          Container:
┌─────────────┐              ┌─────────────┐
│  App         │              │  App         │
│  Libraries   │              │  Libraries   │
│  Guest OS    │              │ (shares host │
├─────────────┤              │  OS kernel)  │
│  Hypervisor  │              ├─────────────┤
├─────────────┤              │  Docker      │
│  Host OS     │              ├─────────────┤
└─────────────┘              │  Host OS     │
                              └─────────────┘
```

### Images vs. containers

An **image** is a read-only template (like an AMI, but for an app instead of a whole server). A **container** is a running instance of an image. You can run many containers from the same image, same as launching multiple EC2 instances from the same AMI.

### The Dockerfile

A `Dockerfile` describes how to build an image, step by step. Example — a minimal static site served by nginx:

```dockerfile
FROM nginx:alpine

COPY ./site /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

Key instructions:

- **`FROM`** — the base image to start from (here, a lightweight nginx image)
- **`COPY`** — copies files from your machine into the image
- **`RUN`** — executes a command *at build time* (e.g., installing packages)
- **`EXPOSE`** — documents which port the container listens on (doesn't actually publish it — that happens at `docker run`)
- **`CMD`** — the command that runs when a container starts from this image

### Building and running

```bash
docker build -t my-static-site .
docker run -d -p 8080:80 my-static-site
```

`-p 8080:80` maps port 8080 on your machine to port 80 inside the container. Visit `localhost:8080` in a browser.

```bash
docker ps                 # see running containers
docker stop <container_id>
docker images              # see images you've built/pulled
```

### A slightly more real example — containerizing a small app

If you have a simple Python (Flask) or Node (Express) "hello world" app, containerize it instead of the static example:

```dockerfile
FROM node:20-alpine

WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .

EXPOSE 3000
CMD ["node", "server.js"]
```

The order here matters for build speed: copying `package*.json` and running `npm install` *before* copying the rest of your code means Docker can reuse the cached "install dependencies" layer on future builds, as long as your dependencies haven't changed — only your actual `COPY . .` layer rebuilds when you edit code. This is a real optimization pattern, not just tidiness.

### Registries — where images live

Just like S3 stores files and ECR/Docker Hub store images. **Amazon ECR (Elastic Container Registry)** is AWS's own image registry — worth knowing it exists even if you don't push to it yet:

```bash
docker tag my-static-site:latest <account-id>.dkr.ecr.us-east-1.amazonaws.com/my-static-site:latest
docker push <account-id>.dkr.ecr.us-east-1.amazonaws.com/my-static-site:latest
```

**Where this connects to your roadmap:** Project 3 used raw EC2 with a `user_data` script. A more modern equivalent replaces that EC2/ASG tier with **ECS (Elastic Container Service)** running containers built exactly like this. You don't need to rebuild Project 3 on ECS right now — just recognize that everything you did with `aws_instance` + `user_data` has a containerized equivalent, and it's a natural "stretch" project later if you want one.

### Checkpoint

Containerize one small app (even a "hello world" API is fine), build it, run it locally, and confirm you can hit it in a browser or with `curl`. No AWS involved yet — this week is purely about understanding Docker itself.

## Week 19: CI/CD Basics with GitHub Actions

**CI/CD** stands for Continuous Integration / Continuous Delivery (or Deployment). The core idea: instead of manually running `terraform plan` and eyeballing the output yourself every time, an automated pipeline does it for you, consistently, on every change.

### GitHub Actions concepts

- **Workflow** — an automated process, defined in a YAML file under `.github/workflows/`
- **Trigger** — what causes the workflow to run (e.g., `on: pull_request`)
- **Job** — a set of steps that run on a fresh virtual machine (**runner**)
- **Step** — an individual command or reusable action within a job

### A workflow that runs `terraform plan` on every PR

Create `.github/workflows/terraform-plan.yml` in one of your Phase 3 project repos:

```yaml
name: Terraform Plan

on:
  pull_request:
    branches: [main]

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3

      - name: Terraform Format Check
        run: terraform fmt -check

      - name: Terraform Init
        run: terraform init
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}

      - name: Terraform Validate
        run: terraform validate

      - name: Terraform Plan
        run: terraform plan -var-file="dev.tfvars"
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
```

### Setting up AWS credentials as GitHub Secrets

Go to your repo → **Settings → Secrets and variables → Actions**, and add `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` as repository secrets. Never put these directly in the YAML file or commit them anywhere — secrets referenced via `${{ secrets.NAME }}` are encrypted and masked in logs.

**A note on the "right" way to do this:** long-lived AWS access keys (even as GitHub Secrets) are considered outdated practice — the modern approach is **OIDC (OpenID Connect)**, where GitHub Actions assumes an IAM role directly, with no stored keys at all, using short-lived credentials issued per run. It's a genuinely better pattern, but it's also a bit more setup than is worth tackling in your first CI/CD workflow. Use access-key secrets to get this working now; treat "set up OIDC instead of static keys" as a good follow-up once the basic pipeline works — and a great thing to mention in an interview as something you're aware of and would want to implement.

### What this actually buys you

Once this workflow exists, every PR you open automatically shows the `terraform plan` output as a check — you (or a reviewer) can see exactly what would change *before* merging and running `apply` manually. This is the automated safety net that replaces "I'll just remember to check the plan output carefully."

### Checkpoint

Add this workflow to one of your Phase 3 repos, open a small PR (e.g., change an instance type), and confirm the Action runs and shows a plan in the PR's checks tab. Intentionally break something (like a syntax typo) in a second PR and confirm the pipeline catches it and fails, the way it should.

## Week 20: Remote State Backend and Terraform Workspaces

Time to revisit the state concepts from Phase 2, Week 8 — but actually build the remote backend this time, and retrofit it into your Project 3 work.

### The bootstrapping problem

Here's a subtlety worth understanding: the S3 bucket and DynamoDB table that will *hold* your remote state can't themselves be created using that same remote state — it doesn't exist yet. The standard solution is a small, separate "bootstrap" Terraform config that uses **local** state (just this once) to create the backend infrastructure itself.

### Bootstrap config — `bootstrap/main.tf`

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "terraform_state" {
  bucket = "your-unique-name-terraform-state"

  lifecycle {
    prevent_destroy = true # a safety net — this bucket should basically never be destroyed
  }
}

resource "aws_s3_bucket_versioning" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id
  versioning_configuration {
    status = "Enabled" # lets you recover a previous state version if something goes wrong
  }
}

resource "aws_dynamodb_table" "terraform_locks" {
  name         = "terraform-locks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }
}
```

Run this once, with plain local state, from its own directory:

```bash
cd bootstrap
terraform init
terraform apply
```

### Pointing Project 3 at the new remote backend

Add this to Project 3's `main.tf` (inside the existing `terraform {}` block, alongside `required_providers`):

```hcl
terraform {
  backend "s3" {
    bucket         = "your-unique-name-terraform-state"
    key            = "project-3/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
```

Then run:

```bash
terraform init
```

Terraform will detect the backend configuration changed and ask if you want to **migrate your existing local state to the new backend** — say yes. Your local `terraform.tfstate` file's contents move into S3, and future runs will read/write there instead, with DynamoDB preventing two people (or two CI runs) from applying at the same time.

**Verify it worked:** your local `terraform.tfstate` file should now be nearly empty (a small pointer, not your actual resources), and you should be able to see the real state object appear in the S3 bucket via the console.

### Terraform Workspaces

A **workspace** lets one Terraform configuration manage multiple, separate state files — commonly used for environment separation as an alternative to Project 3's `.tfvars`-file approach:

```bash
terraform workspace new dev
terraform workspace new prod
terraform workspace select dev
terraform workspace list
```

Inside your config, `terraform.workspace` gives you the current workspace's name as a string — useful for tagging or naming resources per environment:

```hcl
resource "aws_instance" "web" {
  tags = {
    Name = "web-${terraform.workspace}"
  }
}
```

**Workspaces vs. separate `.tfvars` files — which to actually use?** Workspaces share the same backend config but store state under different keys automatically — less setup, but it's easy to forget which workspace you're currently in and accidentally apply against the wrong one (a genuinely common real-world incident). Separate `.tfvars` files, like Project 3 used, make the target environment explicit on every command (`-var-file="prod.tfvars"` is hard to run by accident) at the cost of a little extra file management. Many real teams actually avoid workspaces for this exact reason and use separate state files/directories per environment instead — it's worth knowing workspaces exist and how they work, but don't feel you need to migrate Project 3 away from its current `.tfvars` pattern. Understanding the trade-off matters more than picking one dogmatically.

### Checkpoint

Project 3 now uses a remote S3 backend with DynamoDB locking (verified by checking the S3 console), and you've created and switched between at least two Terraform workspaces in a scratch project to see `terraform.workspace` and state separation work firsthand — even if you don't end up using workspaces in Project 3 itself.

## Glossary — quick reference

| Term                    | One-line definition                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------- |
| Feature branch          | A branch off`main` for one change, merged via PR                                          |
| `.terraform.lock.hcl` | Provider version/checksum lock file — commit this, unlike`.terraform/`                   |
| Image (Docker)          | A read-only template an app container runs from                                             |
| Container               | A running instance of an image                                                              |
| Dockerfile              | Instructions for building an image                                                          |
| ECR                     | AWS's Docker image registry                                                                 |
| CI/CD                   | Automating build/test/plan (CI) and deployment (CD) on code changes                         |
| GitHub Actions workflow | A YAML-defined automated process triggered by repo events                                   |
| Runner                  | The VM a GitHub Actions job executes on                                                     |
| OIDC (for CI)           | Short-lived, keyless AWS credentials for CI — the modern alternative to static access keys |
| Bootstrap config        | A small, locally-stated Terraform config used to create the remote backend itself           |
| Remote backend          | Shared external state storage (e.g., S3 + DynamoDB lock table)                              |
| Workspace               | A way for one Terraform config to manage multiple separate state files                      |
